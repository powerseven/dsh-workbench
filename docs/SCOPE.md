## 一、一句话定界

不做 OKR 方法论工具，做一个**个人工作计划台**：

- **四条主线**：待办 · 工作计划 · 子计划 · 委派
- **两个维度**：分级（层级深度）· 重要程度（决定管控强度）

判断标准：日常真正在用的只有三件事——**记一条待办、拆一个计划、交给别人一件事**。
产品围着这三件事做就够了，不要把方法论搬进来。

## 二、四个核心概念

| 概念 | 是什么 | 设计要点 |
|---|---|---|
| **待办** | 最小执行单元 | 可以**独立存在**（不挂任何计划）——这就是收件箱；挂在计划下时是叶子 |
| **工作计划** | 一段有周期、有目标的工作 | 可含子计划，也可直接含待办 |
| **子计划** | 计划里再分计划 | 深度不限。**这就是「分级」的实现方式**，不另造一套层级概念 |
| **委派** | 把节点交给别人 | 必须带**回执**与**验收**，不能交代完就不管 |

## 三、两个横向维度

### 分级（level）

层级深度本身就是级别，不需要额外字段：

```
年度工作计划 → 季度安排 → 月度计划 → 周计划 → 待办
```

缩进即层级，深度不限。用户不必先去定义一套层级体系再开工。

### 重要程度（priority）→ 管控强度

**这是本模型的核心机制**：重要程度不是一个彩色标签，而是决定这个节点
要走多少流程。

| 重要程度 | 管控要求 |
|---|---|
| **高** | 必须有周期与负责人；进度定期更新；落后预警；完成需**证据 + 验收** |
| **中** | 有截止日期；到期提醒；完成需证据 |
| **低** | 只记录，不催；勾选即可 |

一句话：**重要的多管，不重要的别啰嗦。**

这解决了通用待办工具的通病——所有事走同一个流程，结果大事没人盯、
小事太吵，最后整个列表失去可信度。

## 四、数据模型：一棵递归树

统一成一个节点，用 `type` 区分两类：

```
计划 (plan) ─┬─ 子计划 (plan)   ← 递归，深度不限
             └─ 待办 (todo)     ← 叶子
待办 (todo) ── 不再往下
```

字段：

```
node
  id         n1 / n2 …
  type       plan | todo
  title      标题
  status     todo: todo | doing | done | dropped
             plan: active | done | dropped
  priority   high | normal | low            ← 决定管控强度
  parent     父节点 id（null = 根级）
  start/end  周期（plan）
  due        截止（todo）
  doneAt     完成时间                        ← 统计与周报的上游
  delegate   { to, at, expectAt, status }    ← 委派
  evidence   []                              ← 完成证据
  metric     { current, target, unit }       ← 量化跟踪（保留原 KR 能力）
  note       备注
  children   []                              ← 递归
```

**进度**仍是派生量、不落盘：计划节点 = 其子节点进度的平均；待办按状态。
（沿用现在这条纪律，见 [DESIGN.md](./DESIGN.md#进度派生量不落盘)。）

**为什么改成递归树**：现在的固定三层（目标 → 关键结果 → 任务）表达不了
「年度 → 季度 → 月度 → 周 → 待办」这种真实链条，也放不下「子计划」。
递归树深度不限，而原来的三层只是它的一个特例——**是简化，不是复杂化**。

## 五、和现状的关系（迁移路径）

现有数据可以**无损映射**，不需要人工整理：

| 现状 | 新模型 |
|---|---|
| 目标 `goal` | 计划 `plan`（根级） |
| 关键结果 `kr` | 计划 `plan`（子计划） |
| 任务 `task` | 待办 `todo` |
| `target` / `current` / `unit` | 原样进 `metric` |
| `owner` / `start` / `end` / `note` / `status` | 原样保留 |

建议分两步落地，**先拿价值、再改结构**：

**第一步 · 不破坏结构（✅ 已完成）**
在现有节点上加三个字段：`priority`、`delegate`、`doneAt`（另加 `startedAt` 与
根级 `inbox[]` 收件箱）。「按重要程度管控」「委派（含回执）」与「完成时间戳」立刻可用，
老数据无感——缺省即旧行为，`plan.json` 不需要迁移。改动集中在 `store.js` 的
字段校验与派生计算、`src/index.js` 的 15 个工具与 7 条 HTTP 路由、面板展示与筛选。

**第二步 · 结构改造（待做，需单独分支 + PR）**
把固定三层换成递归节点树，支持任意深度的子计划（DoD 的「计划可嵌套至少 5 层」
属于这一步）。迁移机械可测（老 `plan.json` 读进来直接转新结构），但要同步改
`store.js`、`src/index.js` 的工具面与现有测试——**这是共享仓库的破坏性变更**，
必须单独一个分支 + PR，否则没人能在一个 diff 里看懂。

## 六、边界

**暂不做**：OKR 权重 / 置信度、看板 / 甘特 / 日历视图、模板、任务依赖、重复任务。

**明确不做**（个人场景无收益的团队功能）：权限角色、跨部门目标对齐、
绩效挂钩、工作量均衡、评论 @ 协作、工时计费、移动端离线。
