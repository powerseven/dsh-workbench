# 功能研究：主流的个人计划 / 规划工具该有什么

> 目的：把「个人工作计划管理」在主流工具里被反复验证过的功能面摊开，
> 对照本插件的现状，回答「还该做什么、先做什么」。
>
> 本文是**功能地图 + 差距判断**，不是承诺；具体做法与取舍理由见
> [DESIGN.md](./DESIGN.md)，排期见 [ROADMAP.md](./ROADMAP.md)。
>
> **范围已收窄（2026-09-14）**：本文的六层模型与 OKR 深化部分作为
> **参考与备选**保留，不作为当前实施范围。当前范围与数据模型以
> [SCOPE.md](./SCOPE.md) 为准——简化为「待办 / 工作计划 / 子计划 / 委派」
> 四条主线 + 分级 + 按重要程度管控。
>
> 研究对象：个人向（Weekdone / Perdoo / Sunsama / Amazing Marvin / IdealWeek /
> Strides / GoalsOnTrack / Todoist / Notion / Obsidian）与通用任务平台
> （ClickUp / Asana / Motion / Vikunja）的功能面，以及它们背后的方法论
> （OKR / SMART / GTD / 周复盘 / PARA）。
>

> 下一步候选见 [ROADMAP.md](./ROADMAP.md)。

## 一、结论先行

**1. 决定工具成败的不是功能数量，而是「复盘节奏」。**
几乎所有资料都指向同一件事：目标类应用 40%–83% 的完成率提升，来自
**强制性的周期性回顾**（双周 check-in、周复盘、季度复盘），而不是界面漂亮。
原文一句话很扎心：「下载了工具但从不做复盘，等于没装。」
→ 对本插件，这既是最大的缺口，也是 **agent 原生**最能碾压的地方（见第六节）。

**2. 度量必须分层，不能只有一把尺。**
主流做法是三层并存：愿景/领域（不定量）→ 目标（定性 + 周期 + 责任人）
→ 关键结果（可量化，带权重与置信度）→ 任务（可勾选）。
本插件已有「量化 KR / 清单 KR」双轨，但**缺权重、缺置信度、缺配速对比**——
而这三样正是「behind-the-plan 预警」的实现前提。

**3. 时间戳是所有统计的上游，缺它一切报表都做不了。**
「本周完成了什么」这个问题，在 `plan.json` 里目前**回答不了**——
因为任务没有 `doneAt`。这是数据模型的真实缺口，挡在周报/复盘前面。

## 二、六层功能模型

主流工具的功能几乎都能归到这六层，并由一条「节奏」把它们串成闭环：

| 层 | 内容 | 主流叫法 | 时间尺度 |
|---|---|---|---|
| L5 愿景与原则 | 使命、3–5 年愿景、价值观、不做什么 | Horizon 4–5 / Purpose | 年 |
| L4 领域与目标 | 生活/工作领域、季度或年度目标（Objective） | Horizon 2–3 / OKR-O | 季 / 年 |
| L3 关键结果 | 可量化结果、配速、风险 | Key Results / KPI | 季 / 月 |
| L2 执行项 | 项目、任务、子任务、依赖 | Projects / Tasks | 周 / 日 |
| L1 节奏 | 日意图、周 check-in、周复盘、季复盘 | Cadence / Review | 日 / 周 / 季 |
| L0 留痕 | 版本、活动日志、完成证据、统计 | History / Evidence | 全程 |

关键点：**L1 不是「又一层功能」，而是把 L5→L2 串起来的那个环。**
没有它，上面几层是一次性填完就烂尾的表格。

## 三、功能域清单（十个域）

按「从想法到复盘」的实际使用顺序排列。每域给出主流做法与本插件现状。

### 1. 捕获（Capture）
- **主流**：全局快速添加、自然语言解析日期（「每周五下午 3 点」）、
  Inbox 收件箱、从邮件/聊天一键建任务、mind sweep（脑中清空）。
- **本插件**：对话让 agent 建（`plan_node_add`），或面板顶部输入框回车——
  落到**收件箱**（顶层待办）。
- **评价**：这一域的形态在 agent 场景下应该反过来——**捕获的入口就是对话本身**。
  用户说「记一下，下周要把台区台账交了」，agent 直接落成任务即可，
  不需要再做一个表单。面板那个输入框是给「人就在面板前」的场景留的，
  成本压到「敲一句回车」。这块不是缺口，是形态不同。

### 2. 结构（Structure）
- **主流**：项目/领域/标签/自定义字段；子任务；可保存视图（Saved Views，
  如「我本周高优待办」）；模板（把重复流程固化）。
- **本插件**：**递归节点树**——`plan`（容器）与 `todo`（叶子）两种节点，
  `children` 递归、深度不限（阶梯分级：年 → 季 → 月 → 周随便拆）。
  重要程度（高/中/低）已落地，就地编辑（改名 / 加子项 / 归位 / 换型 / 删除）已落地。
  **无标签、无模板、无保存视图**。
- **评价**：早期写死的三层 `goal → kr → task` 已换成递归树，因为层级深度是
  **需求**不是约束（见 DESIGN.md「结构」一节）。剩下的是规模问题：
  树一大就看不完，**筛选/视图保存**是下一个刚需（筛选条当前是预置的几种）。

### 3. 度量（Measure）
- **主流**：
  - KR 类型多样：指标型（metric）、里程碑型（milestone）、基线型（baseline）、
    反向指标（越低越好）；
  - **权重**（Weight）：重要 KR 占 60%、次要占 10%，进度按权重折算而非按个数平均；
  - **置信度**（Confidence）：本周对「能否达成」的主观把握（Weekdone 的核心），
    置信度下滑即触发求助；
  - **配速 / 轨迹**（Pace）：实际进度 vs 按时间应该到的位置，落后即预警
    （IdealWeek 的 "behind-the-plan alerts"）。
- **本插件**：量化（`current/target/unit`）+ 清单（子节点平均）双轨自动识别，
  对任意层级的节点都成立（`nodeProgress` 递归）；进度是纯函数派生量。
  **配速已补上**（`pace` / `behind`：期望进度 vs 实际进度，差 ≥ 15 个百分点标出，
  与逾期分开）；**仍无权重、无置信度、无里程碑型 KR。**
- **评价**：双轨自动识别是本插件的一个亮点（避免逼用户给不可量化的东西编数字），
  应保留。配速已完成——它只需要 `start/end` + 当前进度，而计划的 `start/end`
  本来就存在，是性价比最高的一项。剩下两项里**置信度**更值得做：
  它携带的是「人的判断」，机器算不出来，而权重只是让汇总换个算法。

### 4. 节奏（Cadence）—— 缺口最大
- **主流**：
  - **日**：Today 视图 / 每日意图 / 每日站会（Sunsama、Akiflow 的核心）；
  - **周**：**PPP 周 check-in**（Plans / Progress / Problems，Weekdone 立身之本）、
    **GTD 周复盘 11 步**（Get Clear → Get Current → Get Creative，1–3 小时）、
    每周 3–5 个 focus items 并评置信度；
  - **季/年**：retro——Google 0–1.0 评分法、根因分类（目标设定/执行/依赖/外部冲击）、
    5-Why 深挖、下周期改进清单；
  - **自动续跑**：复盘任务完成后自动生成下一周期（recurring review）。
- **本插件**：**完全没有。** 计划是「填进去、勾掉」的静态结构，
  虽然节点有了 `startedAt` / `doneAt`，但没有任何周期性的促动机制。
- **评价**：这是主流共识里最关键的一环，也是当前最大的空缺。
  但在本插件里它**不该做成又一套 UI**，而应交给 agent 驱动（第六节详述）。

### 5. 视图（Views）
- **主流**：列表、看板、日历、时间线/甘特、仪表盘——**同一份数据的多种投影**，
  且视图间拖拽同步。
- **本插件**：树形视图（+ 进度条 + 勾选）+ 看板视图（表头「树 / 看板」切换，
  按顶层计划分列、待办摊成卡片，复用同一份 `/get` payload，零新增工具/路由）；
  **详情编辑页**（节点 ✎ / 表头「＋ 新建」打开，整块替换面板，一屏改完全部字段，
  同样零新增工具/路由）。
- **评价**：看板（按顶层计划分列）成本最低、收益最直接，已完成；日历与已有插件
  `magicOF2/dsh-schedule` 功能重叠，需先确认边界；甘特需要任务有起止日期，
  数据模型要先扩。详情编辑页补的是**「人能不能改」**这一侧——此前 agent 能写
  全部字段、面板只能改标题与状态，AI 生成的草稿甚至没法在落库前改，
  这是 agent 原生工具最容易漏掉的一半。

### 6. 时间（Time）
- **主流**：due date、start date、预估工时、**重复任务**（recurring）、
  时间块（time blocking）、日历同步、逾期/即将到期智能列表、提醒与 snooze。
- **本插件**：任务只有 `due`；面板会对逾期标红。目标有 `start/end`。
  **无 start、无预估、无重复、无提醒。**
- **评价**：**重复任务**对个人计划意外地重要（周报、月度对账、季度复盘都是重复的）。
  时间块/日历同步则与本插件定位冲突——那是 Motion/Sunsama 的战场，不必抢。

### 7. 依赖与关联（Dependency & Linking）
- **主流**：blocking / blocked-by、关键路径、甘特可视化；
  以及**任务与目标的显式关联**（task-to-goal linking，解决「两张皮」）。
- **本插件**：待办天然挂在计划下（结构与层级无关，随便挂在哪一层都算关联），
  **关联是结构自带的**，这一点已经赢了大部分「任务和 OKR 分两个模块」的工具。
  **Obsidian 文件库关联已补上**：任意节点可挂 `files[]`（文件或文件夹，指向
  vault 内相对路径），面板点开直达（`obsidian://`）、失效会标出；AI 可用
  `plan_file_read` 列文件夹、读笔记——「我想某个计划时，AI 告诉我有什么文件」
  成立了。它与「任务 ↔ 会话 / 产物」的关联（证据的双向查询）仍是两回事，
  后者未做。**任务间依赖仍缺**。
- **评价**：个人场景下任务依赖价值有限，优先级低。文件关联的价值在
  「计划不孤立于资料库」，成本远低于任务依赖，先做了。

### 8. 证据与留痕（Evidence）
- **主流**：完成时留证据（附件、链接、截图）；活动日志（谁在什么时候改了什么）；
  有的工具（`dsh-todo-guard`）把完成分成**有证据 verified / 假证据 blocked /
  无证据 unverified** 三态。
- **本插件**：有版本留档（`.versions/` 快照 + 回滚，标签记着改动原因），
  这一层强于主流个人工具；`doneAt` / `startedAt` 也已补上；
  **完成证据已补上**（`evidence[]` 追加式，五种类型，文件类会核验是否存在）。
  **但仍无逐操作的活动日志**（快照是每次变更前后的整棵树，
  能回答「那时候是什么样」，不能回答「是谁在什么时候改了哪个字段」）。
- **评价**：**「防假打勾」是本插件的独有议题**——因为这里是 AI 在打勾。
  人类工具不需要防自己，但一个会自己标完成的 agent 需要。
  落地时做了一个与直觉相反的选择：**不强制附证据**，因为硬拦会诱使 agent
  顺手编一条假证据（那比没有证据更糟，你会以为它是真的）；改成
  「无证据的完成项进清单 + 筛选 + 面板 ⊘」，让「AI 说它干完了」可被一次性审查。
  注意 `dsh-todo-guard` 的**三态**（verified / blocked / unverified）与本项目的
  两态（有证据 / 无证据）不同——它多的是「假证据」这一态，而判定「假」需要一个
  独立的验证者，本插件没有这个角色，所以不假装能判。**逐操作活动日志仍未做**，
  它是「谁在什么时候改了什么」这一问的唯一答案，留给后续。

### 9. 报告与统计（Reporting）
- **主流**：自动生成周报/月报；完成率、达成率、时间分配、逾期分布、
  燃尽图；导出（PDF/CSV/Markdown）、定时推送。
- **本插件**：`PLAN.md` 视图可读可 diff，但没有**面向时间维度的统计**。
- **评价**：这正是本工作区已有 docx/周报链路的用武之地——
  数据源现成，产出物交给 agent 生成更合适（见 ROADMAP 的判断）。

### 10. 自动化与 AI（Automation）
- **主流**：AI 起草目标、AI 拆解任务、AI 扫描周报把工作项映射回 KR、
  风险预警、规则引擎（状态变更触发动作）。
- **本插件**：agent 能主动读写计划——这是定位里写明的、相对普通 Todo
  应用的碾压性优势，也是本插件存在的理由；**面板顶部常驻 AI 助手**（第一入口，
  既能问也能记：掌握当前与归纳的全部信息、按需读 vault、给出专家意见与选项，
  人设在 `plan/agents.md` 可改）。
- **评价**：这一域本插件领先，且「用得浅」已经补上一半——现在不只是增删改，
  还能回答「我现在该做什么」「哪个方向没动」，并在新增任务时结合历史给出判断。
  **仍缺周期性的主动促动**（每天 / 每周主动来问一次）。

## 五、个人场景该砍掉什么

主流清单里有大量**团队/企业**功能，对「个人工作计划管理」是纯负担，明确不做：

- 权限与角色（RBAC）、SSO、审计合规
- 跨部门目标级联与对齐矩阵、悬空目标检测
  （个人只有一个「上级」：自己的愿景）
- 绩效评分挂钩、1-on-1 辅导模块、敬业度调查
- 工作量均衡（跨人分配）、资源与产能规划
- 评论/@提及/协作通知（个人场景 = 自言自语）
- 工时计费（除非要对外报价）
- 移动端/离线（宿主是 `dsh web`，场景就在桌面前）

一句话：**保留「方法论」与「节奏」，砍掉「组织」与「协作」。**

## 六、agent 原生带来的重构

这是本文最有价值的一节。**agent 在场时，几项主流功能的形态会变，不能照搬。**

| 主流功能 | 常规形态（人要付出） | agent 在场时的形态（人省下） |
|---|---|---|
| 捕获 | 打开 App、找对列表、手动输入 | 对话里说一句，agent 落库并归到正确 KR 下 |
| 目标拆解 | 自己对着模板憋 KR | agent 读背景（会话/文档）直接出草稿，人只做取舍 |
| 周 check-in | 每周固定 1 小时，多数人坚持不了 | agent 扫计划 + 一周会话，**自动起草**进展/风险/下周重点 |
| 周复盘（GTD 11 步） | 1–3 小时清单式过一遍 | agent 跑清单、把结论结构化落回计划 |
| 完成打勾 | 人自己勾 | agent 干完自己勾（已有） |
| 完成验证 | 人不需要防自己 | **需要防 AI 假打勾**：要求附证据 |
| 报告 | 手工汇总周报 | agent 从 `plan.json` + 时间戳直接生成 docx |
| 风险预警 | 自己发现落后了 | agent 算配速，主动提醒「这条 KR 落后 3 周」 |

**因此本插件的能力建设优先级应当和普通工具不一样**：
不是先补「更多视图」和「更多字段」，而是先把 **agent 能自动完成的那些环节**
打通——因为那才是这个形态独有的价值。

一个反面提醒：现在 agent 在这个插件上只学会了**增删改查**（十来个 CRUD 工具），
等于把 AI 当成了一个更麻烦的表单。真正该会的是**判断**：拆解、扫描、预警、复盘。

## 八、数据模型缺口（动手前先看）

`plan.json` 当前字段（schema 2，递归节点树）：

```
plan : schema, version, title, createdAt, updatedAt, nodes[], lastReason
node : id, type('plan'|'todo'), title, status, children[]（仅 plan）
       可选：owner?, priority?, start?, end?, due?, metric?{target,current,unit},
             note?, delegate?{to,at,status,expectAt?}, doneAt?, startedAt?,
             evidence?[{kind,ref,note?,at}]
```

`plan` 类型节点的合法状态是 `active/done/dropped`，`todo` 是 `todo/doing/done/dropped`；
两者可以原地互换（`type`），但**待办是叶子**，有子节点的计划不能降级为待办。
层级深度不写死，`children` 递归下去。

另有三个**派生量不落盘**（读时算，见 DESIGN.md「进度」一节）：
`progress`（递归完成度）、`pace` / `behind`（配速与落后）、
`unverified`（已完成但无证据）。

按上面的优先级，还没做的字段：

| 字段 | 挂哪 | 支撑哪些功能 | 备注 |
|---|---|---|---|
| ~~`doneAt` / `startedAt`~~ | 任意节点 | 周报、完成统计、在制时长 | ✅ 已完成（第一步） |
| ~~`priority`~~ | 任意节点 | 管控强度、筛选 | ✅ 已完成（高/中/低，默认中） |
| ~~`evidence[]`~~ | 节点 | 防假打勾、任务↔产物 | ✅ 已完成（五类，追加式，file 类核验存在性） |
| `weight` | plan | 加权进度、配额汇总 | 默认 1（等权，向后兼容） |
| `confidence` | plan | 风险识别、agent 预警 | 0–1，**只有人/agent 能给出这个数**，机器算不出 |
| `start` | todo | 甘特、时间线 | （计划已有 `start`，待办只有 `due`） |
| `updatedAt` | 节点 | 「长期未动的节点」预警（FR-A4 剩余项） | 现在只有整棵树的 `updatedAt` |
| `tags[]` | 节点 | 筛选、视图 | — |
| `estimate` | todo | 规划准确度 | — |
| `recur` | 节点 | 重复任务（复盘/周报本身） | — |

**兼容性要求**：全部为可选字段，缺省时行为与现在完全一致；
`schema` 自增与 `.versions/` 归档机制不变，老格式在**读取时自动迁移**、
不回填历史快照（见 DESIGN.md「迁移」一节）。

## 九、一句话总结

主流工具的功能面已经很成熟，本插件在**数据模型、版本留档、agent 读写**
三点上已经站在了前面；缺口经过前三步的补齐，已经从「时间维度」移到了**「节奏」**：

- 原始短板是「没有 `doneAt` 就没有统计，没有周期就没有复盘」——现在**数据齐了**
  （完成时间、配速、证据、委派回执都在），但**没有任何周期性的促动机制去消费它们**：
  没有周复盘、没有周报，落后了也没人主动说。
- 换句话说，剩下的最大缺口不再是「缺数据」，而是「**缺一个按时来问的人**」。
  而这件事恰好应该由 agent 做、并做成 skill 而不是又一套 UI——
  这是本插件形态独有的机会，也是下一步的主战场。

**所以下一步的重点不是「加更多功能」，而是「把计划变成有时间轴的活物」**：
`doneAt` 已补上（第一步），接着让 agent 把周复盘/周报跑起来。
