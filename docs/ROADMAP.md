## 下一步候选

按「缺口大小 × 你的实际痛点」排序，动手前应先确定优先级。

### 1. 日报 / 周报自动生成

**缺口最大**，而且你工作区里已经有周报模板和 docx 产出链路，接起来最快。

方向：做成 **skill 而不是插件**。理由是产出物是文档（docx/邮件/飞书消息），
属于「每次形态都不一样」的任务，用插件硬编码不如让 agent 读计划后自己生成。
数据源现成——`plan.json` 里已有任务状态、截止日期、进度。

要补的数据：任务需要记录**完成时间**（当前 `plan.json` 里没有），
否则无法统计「本周完成了什么」。这是数据模型的一个真实缺口，
做这个功能前要先补 `task.doneAt`。

### 2. 就地编辑

面板现在只能勾选，不能改标题、不能加任务、不能拖拽排序。
最小可用版本：双击标题改名、行内「+」加任务、目标/KR 的增删。

注意：写路径必须和 agent 工具共用同一套 `store.js` 逻辑（含版本归档），
不要在前端另写一套写入逻辑——那会让版本留档出现盲区。

### 3. 看板 / 甘特 / 日历视图

同一份数据的另外三种投影。看板（按状态分列）成本最低、收益最直接；
甘特需要任务有起止日期，当前只有 `due`，数据模型要先扩；
日历可以复用 `magicOF2/dsh-schedule` 的思路，但先确认是否与其功能重叠。

建议先做看板，观察是否真的比树形视图好用再决定要不要做甘特。

### 4. 任务完成时间与节奏统计

`task.doneAt` 补上后可做：每周完成数、计划达成率、逾期分布。
这是日报/周报的上游依赖，优先级应排在它前面。

## 有意不做的部分

### 接单 / 续跑（AI 自动执行的后半段）

`dsh-task-panel` 已经做了「发布任务 → 子 agent 串行执行 → 自动复核 → 待验收」，
`dsh-todo-board` 做了「三档执行模式（提醒／当前会话续跑／自动新开会话）」。
这两个都比重新实现更成熟，而且它们管的是**会话调度**，与本插件管的
**计划数据**是两件事。

正确做法是**分工而非重叠**：本插件专注计划的编辑与跟踪（数据层），
执行调度交给它们。若要联动，让本插件的任务能被派发出去即可，
而不是自己造一套调度器。

### JSON 之外的第二真相源

不要为了「方便手改」而让 `PLAN.md` 变成可写。详见
[DESIGN.md](./DESIGN.md#数据模型为什么-json-是真相markdown-是视图)。

## 技术债

- `src/index.js` 里 10 个工具的参数定义与 `store.js` 的字段校验有重复，
  字段增删要改两处。规模再大就该抽一层 schema。
- 客户端面板没有做乐观更新，勾选后要等一次往返。计划小，暂可接受。
- 面板未处理 `betterSidebar` 之外的其他宿主（如 `AKS1st/dock` 的
  `ctx.workbench` 注册表）。目前只挂 better-sidebar。
