# 需求方案（PRD）：个人工作计划台

**版本** v0.2 · 2026-09-14 ｜ **状态** 已评审通过；MVP 分两步实施，**第一步已完成**
**读者** 产品 / 开发 / 使用者本人
**载体**：DSH（DeepSeek Harness）插件——能力一律落成 **agent 工具 + 侧边栏面板** 两个面，
不做独立 web 应用（理由见 [DESIGN.md](./DESIGN.md#定位为什么是插件而不是独立应用)）

## 0. 一句话

给**一个人**用的工作计划台：把散在脑子、聊天记录和会议里的**待办**收进来，
按**计划 → 子计划**组织，能**委派**出去并跟踪，用**重要程度**决定该管多严，
让 AI 替你更新进度、写周报。

## 1. 需求提取：从原话到需求

需求方不是产品经理，原话是零散的。下表把原话映射成可执行的需求——这是本方案的地基。

### 显性需求（你说过的）

| 原话 | 提炼出的需求 | 编号 |
|---|---|---|
| 「主要是作为个人工作计划管理」 | 单人使用，不是团队协作工具 | G-1 |
| 「可以从待办…做成」 | 待办是基本单元，且能独立存在 | FR-C1 |
| 「工作计划、子计划」 | 计划可嵌套，层级不限 | FR-P1 |
| 「可以分级」 | 层级深度本身就是级别，不另造体系 | FR-P2 |
| 「委派」 | 事项可交给他人，并且要跟得住 | FR-D1 |
| 「分重要程度管控」 | 重要程度决定流程繁简，**不是标签** | FR-M1 |
| 「AI 能主动更新你的计划进度」 | agent 必须能读写计划，且这是核心价值 | FR-A1 |
| （既有）计划版本留档 | 每次变更前留快照，可回滚 | FR-H1 |
| （既有）工作区有周报/docx 链路 | 要能自动出周报 | FR-R1 |

### 隐性需求（你没直说，但逻辑上必需）

| 隐性需求 | 为什么必需 |
|---|---|
| **委派要有回执与验收** | 只有「指派给谁」字段的委派是假委派——交代完就石沉大海，等于没做 |
| **任务要有完成时间** | 没有时间戳，「本周做了什么」永远回答不了，周报只能靠回忆 |
| **计划要能跨会话保留** | 一次会话做完就散，就不叫计划 |
| **数据要能被人读懂、能带走** | 工具会换，计划不能锁死在工具里 |
| **面板与 agent 必须改同一份数据** | 两套真相源必然漂移，而漂移是最难查的一类 bug |

### 明确不做（非目标）

团队协作与权限角色 · 跨部门目标对齐（级联/对齐矩阵）· 绩效挂钩 · 工作量均衡 ·
日历与自动排程（那是 Motion/Sunsama 的战场）· 甘特图 · 工时计费 · 移动端离线。

一句话：**保留「计划」与「跟踪」，砍掉「组织」与「协作」。**

## 2. 问题定义

**现状**：待办散落在聊天记录、微信、会议纪要、便签里；计划写在文档里，写完就没人看；
委派出去的事没有回音；周报靠回忆拼。

### 三个核心问题

1. **收不进来** —— 事情发生的地方（对话、会议）和记录的地方不是同一处，靠手动誊抄必然漏。
2. **跟不上** —— 计划是静态文档，没有推进机制，做完即烂尾。
3. **管不对** —— 所有事走同一个流程：大事没人盯、小事太吵，最后整个清单失去可信度。

### 目标

- 让「记下来」的成本趋近于零
- 让「跟进度」由 AI 承担，而不是靠人的自律
- 让「管多严」与「多重要」匹配

## 3. 用户与场景

**用户画像**：一个人，在 DSH 里干活。有周期性产出（周报）、有需要委派给同事的事、
有按季度/月度组织的计划，愿意把 AI 当协作者而不是工具。

### 场景故事线（一周）

| 时点 | 发生了什么 | 系统该做什么 |
|---|---|---|
| 周一早 | 「把上周遗留和我这周要交的理一下」 | 读计划，列出逾期项与本周到期项；我把其中两件标成「高」 |
| 周三 | 同事在群里让我整理一份数据 | 记一条待办挂到「Q4 计划」下，标「中」，截止周五 |
| 周三下午 | 领导让我牵头做一件事 | 建一个子计划，委派给张三，写清期望完成时间 |
| 周四 | agent 干完一件事 | 自己把对应待办标完成，并附上产出的文件路径 |
| 周五下班前 | 「出个周报」 | 从计划里取本周完成/进行/风险，生成 docx |
| 周日 | 系统提醒 | 有一条委派给张三的事项逾期未回执，我去问一下 |

### 关键场景清单

| 编号 | 场景 | 成功标准 |
|---|---|---|
| SC-1 | 对话里说一句话，事项落库并挂到正确位置 | 不需要手动打开任何界面 |
| SC-2 | 把一个计划拆成子计划与待办 | 层级不限，缩进即层级 |
| SC-3 | 把一件事委派给张三并设期望完成时间 | 能看到「我委派出去的」列表与逾期委派 |
| SC-4 | 标记重要程度，看到它真的改变了行为 | 高优先级的会被预警、被催、要证据 |
| SC-5 | agent 干完活自己打勾并附证据 | 完成后能查到「谁、何时、凭什么完成的」 |
| SC-6 | 一句话生成周报 | 内容来自计划数据，不靠回忆 |
| SC-7 | 一键回到三天前的计划 | 版本留档可见、可回滚 |

## 4. 功能需求

优先级：**P0 = MVP 必须上线**，P1 = 第二期，P2 = 以后再说。

### M1 捕获（待办）

| 编号 | 需求 | 优先级 |
|---|---|---|
| FR-C1 | 待办可**独立存在**（不挂任何计划），构成收件箱 | P0 |
| FR-C2 | 可通过对话创建，agent 自动判断该挂到哪个计划下 | P0 |
| FR-C3 | 字段：标题、状态、截止、备注、重要程度 | P0 |
| FR-C4 | 收件箱批量整理（把游离待办归位） | P1 |

### M2 计划与分级

| 编号 | 需求 | 优先级 |
|---|---|---|
| FR-P1 | 计划可嵌套子计划，**深度不限** | P0 |
| FR-P2 | 缩进即层级，不强制用户先定义层级名称 | P0 |
| FR-P3 | 字段：标题、周期（起止）、负责人、状态、重要程度 | P0 |
| FR-P4 | 进度 = 其下所有节点进度的汇总（**派生量，不落盘**） | P0 |
| FR-P5 | 折叠/展开，默认只展开高优先级与未完成的 | P1 |
| FR-P6 | 计划模板（「周报流程」「月度对账」等） | P2 |

### M3 委派

| 编号 | 需求 | 优先级 |
|---|---|---|
| FR-D1 | 任意节点可委派给某人，记录对象、委派时间、期望完成时间 | P0 |
| FR-D2 | 委派有**回执**：待接受 / 已接受 / 已拒绝 / 已交回 | P0 |
| FR-D3 | 委派有**验收**：完成后由我方确认（同意 / 打回） | P1 |
| FR-D4 | 「我委派出去的」独立视图，含逾期委派提醒 | P0 |
| FR-D5 | 委派对象可扩展到 agent（把事项派给 AI 执行） | P2 |

### M4 重要程度与管控（本产品的核心机制）

| 编号 | 需求 | 优先级 |
|---|---|---|
| FR-M1 | 三档重要程度，**决定管控强度**而非仅作标签 | P0 |
| FR-M2 | 高：强制周期与负责人；进度需定期更新；落后预警；完成需证据 | P0 |
| FR-M3 | 中：需有截止；到期提醒；完成需证据 | P1 |
| FR-M4 | 低：只记录，不提醒不催 | P0 |
| FR-M5 | 落后判定：按周期已过时间比例 vs 实际进度，落后即标记 | P1 |

> M4 的落地状态（见「实施进度」第三步）：FR-M1/M2/M4 的**机制**已完整——
> 周期与负责人以警告形式提示（不硬拦，理由见 §2 与 DESIGN）、落后预警已实现
> （FR-M5）、完成证据已实现（但**不强制**，见 FR-A3 的注）。
> 还剩 FR-M2 的「进度需定期更新」没有独立机制——它的实际形态是
> agent 每次读计划都会看到 `behind` 清单，属于「让落后可见即促更新」，
> 没有也不打算做「多久没更新就报警」的定时器。

### M5 进度与视图

| 编号 | 需求 | 优先级 |
|---|---|---|
| FR-V1 | 树形视图：层级 + 进度条 + 重要程度 + 委派对象 + 截止 | P0 |
| FR-V2 | 勾选完成直接回写（面板与 agent 改同一份数据） | P0 |
| FR-V3 | 筛选：高优先级 / 我委派出去的 / 本周到期 / 逾期 | P0 |
| FR-V4 | 就地编辑（改名、加子项、排序），不必每次都找 agent | P1 |
| FR-V5 | 看板视图（按状态分列） | P2 |

### M6 复盘与报告

| 编号 | 需求 | 优先级 |
|---|---|---|
| FR-R2 | **完成时间戳 `doneAt`**，支撑所有时间维度统计 | **P0** |
| FR-R1 | 一句话生成周报/月报（完成项 / 进行项 / 风险项 / 下周重点） | P1 |
| FR-R3 | 周期复盘：agent 扫计划 + 会话，起草「进展 / 卡点 / 调整」 | P1 |
| FR-R4 | 统计：本周完成数、逾期分布、委派回执率 | P2 |

### M7 agent 能力（差异化核心）

| 编号 | 需求 | 优先级 |
|---|---|---|
| FR-A1 | agent 可读全量计划 | P0 |
| FR-A2 | agent 可增删改节点、改状态、回写进度 | P0 |
| FR-A3 | agent 标记完成时**应附证据**（文件路径 / 会话 id / 命令输出）；无证据的完成项必须可被一次性审查 | P1 |
| FR-A4 | agent 能主动预警：落后项、逾期委派（长期未动的节点待定） | P1 |
| FR-A5 | agent 主动拆解：把一句话目标拆成计划 + 子计划 + 待办草稿 | P1 |

> **FR-A3 的用词是刻意的**：原稿写「**必须**附证据」，实现时改成「应附 + 无证据可审查」。
> 理由是硬拦会激励造假——在打勾那一刻要求必须附证据，agent 最省事的路径是
> 顺手编一条假证据，**那比没有证据更糟，因为你会以为它是真的**。
> 所以走「允许无证据完成，但把它列进可审查清单」：`plan_show` 的 `unverified` +
> 面板 `⊘` + 一个「无证据的完成项」筛选。`kind: 'file'` 的证据会被核验
> （查文件是否存在），其余四种只记录、不假装能验。
>
> **FR-A4 的「长期未动的节点」没有做**：它需要一个「多久没动」的判据，
> 而现在只有 `doneAt` / `startedAt`，没有「最后修改时间」这类字段。
> 加一个时间戳字段就能做，但优先级低于其余项——暂不引入。

### M8 留档与数据主权

| 编号 | 需求 | 优先级 |
|---|---|---|
| FR-H1 | 每次变更前自动快照，可列可回滚 | ✅ 已有 |
| FR-H2 | 计划为工作区内可读文件（JSON 真相 + Markdown 视图） | ✅ 已有 |
| FR-H3 | 本地私有，不进共享仓库 | ✅ 已有 |

## 5. 非功能需求

| 编号 | 需求 | 说明 |
|---|---|---|
| NFR-1 | **写入路径唯一** | 面板、agent、HTTP 面共用同一套存储逻辑（含版本归档），不许前端另写一套 |
| NFR-2 | **进度是派生量** | 不落盘，避免两个真相源漂移 |
| NFR-3 | **向后兼容** | 新增字段一律可选，缺省行为与现状一致，不回填历史数据 |
| NFR-4 | **可回滚** | 任何变更前有快照，回滚本身也可撤销 |
| NFR-5 | **数据可携带** | JSON + Markdown，随时能读、能迁移 |
| NFR-6 | **隐私** | 计划是个人工作数据，本地私有 |

## 7. 分期规划

递归树模型 · 待办 + 计划 + 子计划 · 委派（含回执）· 重要程度三档与高优先级管控 ·

### V2（P2）——「按需长出来」

看板视图 · 计划模板 · 委派给 agent 执行 · 统计报表。

## 8. MVP 验收标准（Definition of Done）

- [ ] 对话说一句「记一下，周五前把 XX 交给张三」，能自动建节点并挂到合理位置
- [ ] 计划可嵌套至少 5 层
- [ ] 「我委派出去的」视图能看到对象、期望完成时间、回执状态，逾期有标记
- [ ] 重要程度为「高」的节点缺周期/负责人时被拦下或警告
- [ ] 完成操作会写入 `doneAt`
- [ ] 面板与 agent 改的是同一份数据，且每次变更都留了快照
- [ ] 现有 54 个测试全绿，且新增测试覆盖新字段与新校验

## 9. 风险与假设

| 风险 | 影响 | 应对 |
|---|---|---|
| 委派是单方记录，同事不在这套系统里 | 「回执」只能靠手工更新 | 明确定位：回执由我方标记，不追求对方在系统内操作 |
| 递归树是破坏性变更 | 老 `plan.json` 需迁移 | **已落地**：读取时自动迁移、老 id 原样保留、回滚老快照也迁移；风险靠「先做不破坏结构的字段加法、再单独分支改结构」拆成两步 |
| 重要程度定不准（人会全标「高」） | 管控机制失效 | 默认「中」；只有「高」走重管控，保住区分度 |
| 需求随工作变化 | 模型反复改 | 字段全部可选 + 核心最小化，压低改动成本 |

**假设（待验证）**

- A1：确实是单人使用，无多人协同需求
- A2：周报是真实且高频的产出
- A3：委派对象是线下/微信里的人，系统只做记录与跟踪

## 10. 怎么判断做成了

| 指标 | 目标 |
|---|---|
| 计划覆盖率 | 本周实际做的事，80% 能在计划里找到 |
| 委派回执率 | 委派出去的事项中，回执状态明确的 > 90% |
| 周报生成耗时 | 从「回忆半小时」降到「一句话」 |
| 计划存活期 | 一个计划从建立到收尾 > 4 周（不烂尾） |

## 11. 决策记录（原「待确认」，2026-09-14 评审通过）

5 项都已拍板。**取舍理由一并记下**——只记结论的话，半年后没人知道为什么这么定。

| # | 问题 | 决定 | 理由 |
|---|---|---|---|
| 1 | 数据模型 | **分两步**：先加 `priority` / `delegate` / `doneAt` 三个字段（不破坏结构），递归树作为第二步单独分支 | 先拿价值、风险可控；三个字段是递归树下的同一批字段，第一步的工作不作废。共享仓库里改数据模型是破坏性变更，值得单独一个 PR 让人看懂 |
| 2 | 重要程度取值 | `high` / `normal` / `low`，界面显示中文 | 程序判断稳定（不受文案改动影响），存储也不受语言环境影响 |
| 3 | 委派对象 | **只做「人」** | 「交给 agent 执行」牵扯会话调度，是另一个问题；混进 MVP 会让范围失焦。V2 再说（FR-D5） |
| 4 | 周报产出 | **docx** | 工作区已有这条链路，接起来最快 |
| 5 | 计划作用域 | **当前工作区**（与 `plan/` 现状一致） | 与「计划与产出同仓、可 git diff」的既有设计一致 |

**实施进度**

- 第一步（已完成）：`inbox` 收件箱 + `priority` + `delegate`（含回执）+ `doneAt`/`startedAt`
  + 管控警告 + 面板的收件箱 / 徽章 / 委派标记 / 筛选条；新增 5 个工具与 2 条 HTTP 路由。
- 第二步（**已完成**）：固定三层 → **递归节点树**（`plan.nodes[]`，`type = plan | todo`，
  `children` 深度不限）。DoD 的「计划可嵌套至少 5 层」达成。要点：
  - 老数据**读取时自动迁移**、写入时落新格式，用户不需要跑迁移脚本；老 id
    （`g1`/`k1`/`t1`）原样保留——历史会话消息与 `.versions/` 快照都还在引用它们；
    新节点统一 `n` 前缀。`restore` 回滚到老格式快照时同样迁移后落盘。
  - 工具面随之收敛：`goal/kr/task` 六件套 → **节点模型四件**
    （`plan_node_add` / `plan_node_set` / `plan_node_move` / `plan_node_remove`）。
    三套 API 做同一件事，agent 每次都得先想「这东西算 goal 还是 kr」，而这些区分
    对人本就没有意义。
  - 收件箱由 `plan.inbox[]` 变为「**顶层待办**」，并由此补上了 FR-C4 的**归位**
    （`plan_node_move`：把游离待办移进任意计划下），同时补上了此前完全缺失的删除。
  - **换型**：`plan_node_set` 支持改 `type`，待办可原地提升为计划继续拆、
    空计划可降回待办（有子节点的计划不允许降级，否则孩子们会变成孤儿）；
    跨类型时状态重新归一。这让「记的时候不用先想清楚它该是计划还是待办」成立。
  - 规模：工具 15 → 13，HTTP 路由 7 → 9，测试 133 → 170。
- 第三步（**已完成**）：**兑现「高」的承诺**——把重要程度这个开关从「只有两条警告」
  补成真的三档有别。对应 FR-M5（落后预警）与 FR-A3 / FR-A4（完成证据与主动预警）。
  - **落后预警**：`pace = (今天 − start) / (end − start)` 与 `nodeProgress` 比，
    差 ≥ 15 个百分点标为 `behind`。四种情况不报：没周期 / `start` 还没到 /
    已过 `end`（那是逾期，两种信号分开才能触发不同动作）/ 已完成或已放弃。
    **待办不讲配速**（待办没有周期，它的落后表现就是逾期）。
  - **完成证据**：`evidence: [{ kind, ref, note?, at }]`，**追加式**；`kind` 固定五种
    （`file`/`session`/`command`/`link`/`note`），缺省 `note`；同 `kind` + 同 `ref`
    不重复追加；只有 `file` 会被核验（文件是否存在，相对工作区根）。
  - **不新增工具、不新增路由**：落后预警是读时算出来的派生量，证据是
    `plan_node_set` / `plan_todo_set` 上的三个可选标量参数（一次一条，要多条调多次）。
    工具 13 个、路由 9 条不变。
  - 暴露路径：`plan_show` 增加 `behind[]` / `unverified[]` 两份清单与
    `control.behind` / `control.unverified` 两个计数；`PLAN.md` 里落后与证据同样落成文字；
    面板增加落后徽章、证据标记（`📎n` / `⊘`）与两个新筛选。
  - **顺带修掉一个真 bug**：`applyFields` 曾经整体替换 `metric`，
    于是「只更新当前值」会把 `target` 静默抹掉（进度从「10/12」变成按状态算）。
    现在逐字段合并——`plan_node_set { current: 10 }` 不再丢数据。
  - 规模：测试 170 → 213（工具与路由数不变，这正是这一版的设计目标）。
