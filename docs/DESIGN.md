# 设计说明

记的是**为什么这么做**，不是做了什么。用法见 [README](../README.md)，
架构与坑见 [AGENTS.md](../AGENTS.md)。

## 定位：为什么是插件而不是独立应用

需求是「基于 dsh web 界面做一个个人工作台」。有两条路：另起一个 web 应用，
或做成 dsh 插件。选了后者，理由：

1. **agent 天然在场。** 独立应用要自己接 LLM、自己管理会话、自己做权限。
   做成插件则直接复用宿主已有的会话、模型、工具审批、文件沙箱。
2. **AI 能主动读写计划。** 这是最大的收益：计划数据通过 `plan_*` 工具暴露后，
   agent 干完活可以自己回写进度。独立应用要做到这点，得额外设计一套 API
   让 agent 调用，而且 agent 还得知道它的存在。
3. **不需要另起服务。** 用户已经在跑 `dsh web`，插件只是组合树里多一行。

代价：绑死在 DSH 的插件机制上，且改动 host 半身需要重启。对这个场景值得。

## 数据模型：为什么 JSON 是真相、Markdown 是视图

计划是一棵需要**程序操作**的树：按 id 定位节点、删改、汇总进度、回滚版本。
两种朴素方案各有硬伤：

- **纯 Markdown 为真相**：人可读、可 diff、agent 能直接读懂。但要程序化增删改查
  就得写一个稳健的 Markdown 解析器；而任何格式漂移（用户手改缩进、agent 写错层级）
  都会**静默丢数据或改错节点**。风险与收益不成比例。
- **纯 JSON 为真相**：结构可靠、校验容易。但人不可读、git diff 不可读，
  agent 也得先解析才能理解——失去了「计划应该能被人一眼看懂」这个基本诉求。

双表示各取所长：**写入永远走结构化路径**（`plan.json`，有校验和版本归档），
**阅读与 diff 走生成的 `PLAN.md`**。代价是二者可能不同步 —— 但同步是单向的
（`PLAN.md` 每次写入都从 `plan.json` 重新生成），所以不会产生冲突，
只会在「有人手改了 PLAN.md」时丢失手改内容，这一点在文件头和 README 里都写明了。

## 结构：为什么是任意深度的树，而不是固定的三层

最早的模型是硬编码的三层 `goal → kr → task`。它的问题不是「不够灵活」这种笼统说法，
而是**三个具体后果**：

1. **层级是需求，不是约束。** 真实计划的分层深度取决于时间尺度——
   年度拆季度、季度拆月度、月度拆周，三层和四层都常见。写死三层等于
   让用户去迁就实现：把「季度」硬塞进 goal、「月度」塞进 kr，剩下的只能写进文本里。
2. **三套 API 做同一件事。** `plan_goal_add` / `plan_kr_add` / `plan_task_add`
   的差别只有「挂在谁下面」，字段几乎重合；agent 每建一个节点都得先判断
   「这算目标还是 KR」——而**这个区分对人本来就没有意义**，它只是实现的产物。
3. **结构约束散落在各处。** 「KR 不能挂 goal 之外的东西」「task 必须有父 KR」
   这类校验要在每个入口重复一遍，每加一种关系就要改所有入口。

改成**递归节点树**：节点只有两种类型 `plan`（容器，可挂子节点）与 `todo`（叶子），
`children` 递归下去，深度不限。收益是结构操作**收敛成四个**，全部作用在任意节点上：

| 操作 | 语义 |
|---|---|
| `node_add` | 建一个节点，`parent` 决定挂哪；不传就进收件箱 |
| `node_set` | 改字段（含 `type`——待办 ⇄ 计划） |
| `node_move` | 换父节点 / 调同层顺序 |
| `node_remove` | 删节点（计划连子项一起） |

「层级」从**结构**变成了**约定**：你想用三层就用三层，想用四层就用四层，
代码里没有一处知道或在乎这件事。代价是**每次遍历都得真的递归**——
早期实现里 `todoCounts` 只扫了顶层、`locate` 把祖父当成了父节点，
都是「按老的三层写」留下的 bug（见 AGENTS.md 坑 #9）。

**收件箱不再是独立字段。** 老模型里 `inbox[]` 和 `goals[]` 并列，是两个集合；
新模型里「顶层待办」就是收件箱——它是**一个位置**，不是一个类型。
这消掉了「收件箱项怎么归位」这类跨集合搬运算，归位退化成一次普通的 `node_move`。

## 换型：为什么允许原地改 type，且拒绝「有子的计划降级」

递归树里，`plan` 与 `todo` 的差别只有一条：**能不能有子节点**。
这条差别在真实使用中会随着认知变化——开会时随手记的「把数据治理做起来」，
事后发现得拆；拆完发现其实不该拆。所以换型是必须支持的，否则用户只能
新建一个计划再把待办搬进去，而多出来的那一层容器**没有语义**（它不是一件事，
只是「为了能拆而造出来的壳」）。

两条约束，理由不同：

- **有子节点的计划不能降级为待办**——待办是叶子，孩子们会变成孤儿。
  结构损伤不可逆，所以宁可报错。这个判断放在数据层（`setNodeType`）而不是 UI 里，
  UI 只是顺手把「⇩」按钮藏起来，避免让用户点了才看到错误。
- **跨类型状态必须重新归一**——`active` 只对计划合法，`todo`/`doing` 只对待办合法。
  这里踩的坑值得单独记：如果不归一，留下的是**一个对该类型非法的状态**，
  而非法状态在本项目里不是报错，是**渲染与统计里的静默错值**（进度算 0、
  筛选漏掉、角标对不上）。凡是「状态集合按类型分叉」的地方都要问一遍
  「跨类型时旧的取值还合法吗」。

## 迁移：为什么读时迁移，而不是写一个转换脚本

从 schema 1 换到 schema 2 会动到**用户已经写在磁盘上的 plan.json，以及
`.versions/` 里的历史快照**。做法上不是提供一个「升级命令」，而是
**读时自动迁移**（`migratePlan` 在 `PlanStore.load()` 里跑，落盘时写成新格式）：

- 要求用户跑一条命令，就会有用户没跑，而失败模式是**静默的**——
  旧的 `goals`/`krs`/`tasks` 字段读不出来，面板显示空计划。用户看到的
  是「我的计划没了」，而不是「请先升级」。
- 迁移必须**无损**：保持老的 id（`g1`/`k1`/`t1`）不变。因为委派、备注、
  快照文件名里都可能引用它们；重新编号会让历史快照指向错误的东西。
- `.versions/` 里的老快照**不迁移**，回滚时按同一套迁移逻辑读进来——
  少一次批量改写，也少一个「批量改写写坏了」的失败点。

## 进度：派生量，不落盘

`nodeProgress` / `planProgress` 都是**算出来的**，不存进 `plan.json`。

原因：一旦把进度存下来，它就会和任务状态不一致（改了任务忘了改进度），
而两个真相源之间的漂移是最难查的一类 bug。现在进度是树的纯函数，
不可能不一致。代价是每次读都要重算，但计划规模小，可忽略。

`nodeProgress` 对任意节点递归成立，这是递归树带来的简洁之处：

1. 有 `metric.target` → 按 `current / target` 量化；
2. 否则有子节点 → 取子节点平均（递归）；
3. 否则是叶子待办 → 按状态（`done` = 100%，其余 0%）。

两种度量（量化 / 清单）都保留，是为了同时容纳「可量化的 KPI」（完成 12 个台区）
和「清单式交付」（建立台账 = 若干步骤）。硬要统一成一种，
会逼用户给不可量化的东西编数字。

同一套理由也适用于后来加的 `pace`（配速）与 `unverified`（完成但无证据）：
它们都是**从已有字段算出来的**，不是新字段。多一个落盘字段就多一个会漂移的
真相源，而「面板显示的落后状态」和「服务端算的落后状态」不一致时，
没人知道该信哪个。

## 管控：为什么是警告而不是拦下

重要程度定为「高」时，产品上要求它必须有周期与负责人。实现上有两条路：
校验不过就**拒绝写入**，或者写进去但**把缺口指出来**。选了后者。

理由是这条产品目标：**「记下来」的成本要趋近于零**（见 PRD §2）。在捕获那一刻
硬拦，最有价值的行为——开会时顺手记一条——会变成一串表单校验，人干脆不记了。
计划烂尾从来不是因为缺一个必填校验，而是因为压根没记下来。

所以 `nodeWarnings()` 返回的是**建议**：agent 在工具返回值里看到它，
面板在节点旁显示 ⚠，仅此而已。缺口的补全由人和 agent 在后续交互中完成。

配套的两个细节也是同一思路：

- **默认 `normal`（中）**。若默认「高」，人人都是高，管控机制立刻失效——
  区分度比严格更重要。
- **待办不强制「负责人」**。待办默认就是自己负责；若硬要求填，每一条高优先级
  待办都会报警告，警告随即变成噪音。只有计划/子计划（需要有人对结果负责）才要求。

## 落后预警：为什么是 15%，以及为什么它不进 ⚠

「重要程度 = 高」承诺了落后预警。数据（`start` / `end` / 进度）一直都在，
缺的只是把两者比一下：`期望进度 = (今天 − start) / (end − start)`，与
`nodeProgress` 相减，差 ≥ 阈值即标出。

**阈值取 15 个百分点**，不是「只要落后就报」。刚开工时「时间过了 5%、进度 0%」
是完全正常的状态；报出来人就会开始忽略这个标记，而**被忽略的标记比没有标记更糟**
——它同时消耗掉「有标记 = 要处理」这个信任，之后真的落后也没人看了。
15% 想表达的是「时间过了一大半、进度还不到一半」这类需要现在调整节奏的偏离。

**四种情况一律不报**，每一种都是为了让信号保持可用：

| 情况 | 判定 | 理由 |
|---|---|---|
| 没填周期 | 不算配速 | 没有基准就没有「落后」——继续走逾期逻辑 |
| `start` 还没到 | 不报 | 「还没开始」不是「落后」 |
| 已过 `end` 没完成 | 不报（走逾期） | **两种信号该触发不同动作**：逾期 = 去问为什么没交付；落后 = 现在调整节奏 |
| 已完成 / 已放弃 | 不报 | 结束的事没有节奏问题 |

**待办不讲配速。** 待办没有 `start`/`end`（它是「一件事」，不是「一段时间」），
所以待办的落后表现**就是逾期**。计划讲配速、待办讲截止，两条线各管一段——
硬给待办加周期，等于逼用户给「交台账」编一个起止日期。

**它不进 `nodeWarnings`。** ⚠ 现在的含义是「元信息不全，补一下就行」；
落后是「执行偏离了，要决策」。把后者塞进前者，两个信号都会变糊。
所以落后做成独立的 `pace` / `behind` + 独立的筛选芯片 + `plan_show` 的 `behind[]`
清单，而不是多一条 ⚠ 文案。同理，它不是新字段——是**算出来的派生量**，
和 `progress` 一样不落盘。

## 完成证据：追加、固定五种、只核验 file、不硬拦

这是本项目**独有的议题**。人类用的待办工具不需要「完成证据」，因为勾是人自己打的；
但这里勾是 **agent 打的**——「AI 帮我标完了」这句话需要有可验证性，
否则进度条就是自说自话。

四个决定：

**一、追加式，不是覆盖。** `evidence` 是数组，补第二条不会抹掉第一条。
证据记的是「这件事是怎么完成的」的连续过程，覆盖语义会让补证变成替换证。
同 `kind` + 同 `ref` 视为同一条（不重复追加）——agent 重试、或人又点了一次
「附上这个文件」，产生两条一模一样的证据只会让审查变糊。

**二、`kind` 固定五种（`file`/`session`/`command`/`link`/`note`），不做智能推断。**
推断会猜错（一个路径既可能是文件也可能是命令），而这类记录**猜错比不猜更糟**——
上限是「记录」，下限是「记错」。agent 自己清楚产出的是文件还是命令。
注意这与「这个算 goal 还是 kr」那种人为区分不同：那种区分是实现的产物，
这种区分是事实。缺省按 `note`（只记录、不核验）——不让「忘了一个枚举值」
变成一次失败的写入，但写错枚举值仍然报错。

**三、只有 `file` 会被核验。** 查文件是否存在是唯一**不会误报**的核验点：
「文件在不在」是客观事实，「这条命令有没有真的跑过」不是。文件产出恰好也是
最常见的形态，所以这一个核验点覆盖了多数实际场景。其余四种只记录、
**不假装能验**——假装能验比不验更危险，因为它会让人以为已经核过了。

**四、不硬拦，靠「一次可审查的清单」。** 允许无证据标 `done`，理由是
「硬拦会激励造假」：在打勾那一刻要求必须附证据，agent 最省事的路径是顺手编一条
假证据，**那比没有证据更糟——你会以为它是真的**。所以走另一条路：无证据的完成项
进 `unverified` 清单 + 面板 `⊘` 标记 + 一个「无证据的完成项」筛选。
**这个筛选才是「防 AI 假打勾」真正落地的地方**：它让「AI 说它干完了」这句话
可被一次性审查，而不是让写入变成一场与 agent 的博弈。

`⚠` 里只对 `high` 档加了一条「完成但没有证据」——那一档才是承诺了完整流程的档位。
全部档位都塞进去，等于每一条完成的待办都挂一个 ⚠，那个标记立刻失去信息量。
`unverified` 则对所有档位都算，只是换一个出口（清单 / 筛选 / `⊘`）。

**入口不新增工具。** 证据是 `plan_node_set` / `plan_todo_set` 上的参数，
因为「打勾」和「附上产出」本来就是同一个动作，没必要让 agent 分两步走。
参数是三个标量（`evidenceKind` / `evidenceRef` / `evidenceNote`）而不是一个对象数组：
工具的 JSON Schema 传标量最稳，而「一次一条、要多条调多次」正好契合追加语义。

## 收件箱：为什么不计入计划完成度

`planProgress` 只对**顶层计划**求平均，顶层待办（也就是收件箱）不参与。两个原因：

1. **语义**：收件箱里的东西还没被承认为「计划」的一部分，把未归类事项计入
   完成度，等于让「没整理」这件事去拉低整体进度——惩罚的是记账习惯，不是执行。
2. **机制**：不计入完成度，但**计入角标、筛选与 `PLAN.md` 的收件箱段**。
   它会一直出现在你眼前，直到被归位或被完成。用「可见」而不是「扣分」来驱动整理。



## 版本留档：为什么不用 git 代替

用户选了「工作区 markdown/JSON + git」，git 本身就有历史。仍然自己做
`.versions/` 快照，理由：

- **不依赖 git。** 工作区可能没初始化 git，或这次改动根本没 commit。
  快照始终存在。
- **留档粒度是「每次变更」而不是「每次提交」。** agent 可能连续改十次才提交一次，
  中间态恰恰是最需要回滚的。
- **回滚代价低。** `plan_restore` 不需要懂 git。

两者互补：`.versions/` 管细粒度、可回滚；git 管跨文件、跨时间的项目级历史。

归档标签取**被归档版本自己写入时的原因**（`plan.lastReason`），而不是本次改动的原因。
这一点踩过坑：最初用本次改动的原因命名，导致标签描述的是「即将发生的事」、
内容却是上一个版本，回溯时会看错。

## 客户端：为什么纯逻辑单独成文件

`logic.cjs` 里放的全是无 React、无 DOM、无 IO 的纯函数（进度格式化、状态标签、
排序、汇总）。这样做是因为**这些逻辑最需要测试，而 React 组件在 Node 里测成本高**。
把它们抽出来后，可以用 `node:test` 直接覆盖边界情况（脏数据、未知状态、
空计划），且这些测试跑得极快（整个套件 < 1 秒）。

`logic.cjs` 被构建脚本内联进 bundle 闭包，UI 代码直接引用其中的函数名，
不经过模块导出——所以它可以用 `typeof window` 守卫来兼顾「Node 里测试」和
「bundle 里不导出」。**但 client 主文件不能这么做**，见 AGENTS.md 的坑 #1。

## 构建：为什么零依赖、不压缩

`scripts/build.mjs` 只做两件事：拷贝 host 的 ESM 文件，把 client 的纯逻辑与 UI
文本内联后包进 C6 工厂。不引入 tsdown/rollup/vite，不压缩不转译。

- 插件总代码量小，压缩收益近乎为零，而**可读的产物直接决定了排查效率**。
- 零构建依赖意味着 clone 下来 `node scripts/build.mjs` 就能跑，没有 `npm install`
  这一层失败点。
- 代价是没有类型检查。当前规模下，测试（247 个）比类型更能挡住真实缺陷 ——
  抓到的 bug（归档标签错位、client 导出被守卫吞掉、`locate` 认错父节点、
  `metric` 局部更新抹掉 `target`）都不是类型问题，而是「约定的含义在别处
  被理解错了」。最后一个尤其典型：类型上 `{ current: 10 }` 完全合法，
  错的是「不传的字段保持不动」这条**约定**没对嵌在对象里的字段成立。

## 就地编辑：三个被手势逼出来的决定

面板上「双击改名 / 拖拽排序 / 折叠展开」这三件事，实现时各自撞上一个不得不
选边的问题。记下来是因为它们都不是风格偏好，而是**约束下的唯一可行解**。

### 单击必须延后

待办标题上，单击 = 切换完成、双击 = 就地改名。浏览器的事件序列是
`click → click → dblclick`——**双击一定会先经过两次单击**。如果单击立即执行，
一次改名就会先把这条待办标成完成（写一次盘、留一个版本快照），再进入改名。
用户看到的是「我就改了个错别字，怎么把它打勾了」。

用 `e.detail` 挡不住：第二次 `click` 的 `detail` 确实是 2，但**第一次早就落地了**。
唯一的办法是让单击排一个 200ms 的定时器，双击到来时把它清掉。

代价是单击切换慢了 200ms。这个代价只加在「点标题」这条便利路径上——
**复选框始终是即时的**，想快就点框。用一个明确的"慢一点但不会误伤"，
换掉一个"快但会顺手把事办了"，这笔账在「改名的频率不低、而且改名的人不期待
附带效果」的前提下是划算的。

### 折叠状态进 localStorage，不进 plan.json

折叠是这一族状态里第一个「看起来像数据」的：它描述树，还带 id。但它属于
**这台机器上这个人现在想看到什么**，不属于计划本身。三个具体后果说明为什么不能
写进 `plan.json`：

1. 它进 `.versions/` 快照——于是「收起一个分支」会在版本历史里留下一条记录，
   把「谁在什么时候改了计划内容」这件事冲淡成噪声。
2. 它跟着 git 提交跑到别人机器上——别人拉下代码打开面板，发现几层是收着的，
   而他从来没做过这个操作。
3. 它需要写盘、需要校验、需要一条 HTTP 路由——**为一个显示偏好新增写入路径**，
   而这个项目的原则是写入路径越少越好（每次写入都要归档）。

放 `localStorage` 后它一行写入路径都不占，且天然是「每台机器各自记」的语义。
代价是换浏览器就没了——对一个显示偏好来说，这正是期望行为。

`localStorage` 在受限环境下会抛异常，所以读写两头都吞掉异常：存不下就退化成
「每次打开都是全展开」。**显示偏好解析失败绝不该让面板打不开**，
因此 `parseCollapsed` 对任何脏数据都返回空数组，而不是抛错。

### 落点合法性只判一处

拖拽的合法性（能不能放进这个节点、会不会成环）由 `dropTarget()` 一个函数回答，
UI 拿它的返回值同时决定两件事：画不画落点指示器、要不要 `preventDefault`。
不重复判断是因为**两边判断迟早会分叉**——UI 说能放、服务端拒绝，
用户得到的是一个语焉不详的报错，而不是一个不让放的落点。

不 `preventDefault` 的副作用正好是想要的：浏览器自己显示禁止光标。
这比自己画一个"无效"标记更省事，也更符合系统级反馈。

服务端**仍然要再拦一次**。这不是重复，是分工：数据层负责不变量（成环的树不该
存在），UI 只负责不让用户白拖一趟。少任何一边都不行——只有服务端拦截，
用户会拖完才看到报错；只有 UI 拦截，别的入口（比如 agent 调工具）就能造出坏树。

### 落点的 `index` 必须换算坐标系

`/node-move` 的 `index` 语义是「**先把自己摘掉**，再在这个下标插入」
（摘除后后面所有节点前移一位）。客户端算落点时必须用同一个坐标系，
否则同层往后拖会稳定差一格。

这类错特别难查：表现只是"顺序没完全对"，很像手滑。所以测试里**不比对数字**，
而是把客户端算出的落点喂给真的 `moveNode`，断言整棵树的形状——
把两边的一致性交给实现本身去证明，而不是交给我对数字的理解。

## 面板样式：为什么改成只用宿主的 design token

面板原来的样式是自己造的一套：颜色写死 hex，灰色一律 `rgba(127,127,127,α)` 现搓，
明暗两态用 `@media (prefers-color-scheme: dark)` 打补丁。功能上没坏，但它怎么调都不像
宿主的一部分——而这正是「界面看着差」的真实来源：**缺的不是好看的颜色，是系统**。

改动的关键是先去看宿主怎么做，而不是自己发明规则。`dsh web` 自带一套完整的三层
token（`--dsw-static-*` 原始层 → `--dsw-alias-*` 语义层 → `--dsw-specific-*` 组件层）
加一套字号阶梯（`--dsw-font-xxxs-11` / `-xxs-12` / `-xs-13`…）。它自己的文档写得很直白：
**「插件消费 `--dsw-*` token，不要自己管主题状态」**。面板做的刚好是它劝你别做的那件事。

### 明暗不能自己判：宿主用的是属性，不是媒体查询

宿主把解析后的方案投射到 `body[data-ds-dark-theme]` 与 `html{color-scheme}`，
并**在 body 上重映射整层 `--dsw-alias-*`**。所以媒体查询是错的——它跟的是系统偏好，
而主题是用户在设置里选的。**「系统深色 + 用户选浅色」时，面板会渲染成深色块。**

改成引用 token 之后暗色是白送的：宿主重映射 alias，面板一行都不用写就跟着翻。
`build.test.mjs` 加了断言，挡住媒体查询那套被写回来。

### 别名层落在面板自己的根上，不在 `:root`

这是本次最容易被静默坑到的一处：`var()` 是在**声明它的那个元素**上完成替换的。
把 `--wb-fg: var(--dsw-alias-label-primary)` 写在 `:root`（html）上，它会在 html 的
上下文里算出浅色值并定死，`body[data-ds-dark-theme]` 的重映射**传不下来**——
token 本身看起来完全正常，只是不翻。声明在 `.dsh-wb-wrap` 上才随上下文一起翻转，
顺带把命名空间收在自己子树里。

### 语义色只上填充，不上文字

把五种自造色收进宿主语义色之后，立刻撞上对比度：宿主那套色里**只有 danger（`#ec1313`）
在白底够 4.5:1**，warn 的琥珀只有 2.8:1、success 的绿只有 2.3:1。硬拿它们当文字色，
就是「看着有颜色，实际读不清」。

所以定了一条规则：**文字只有两级中性色（primary / secondary，白底 5.8:1），语义色
只出现在填充、描边与符号上**；需要区分时用「软底 + 深字」（如「落后 18pt」是琥珀软底
配近黑字，17.5:1）。同理把「低优先级」原来的浅灰改成中性色 + 去掉描边——
**层级靠字重、描边与留白表达，不靠把对比度压下去**。

顺带删掉一个「宿主意料之外的颜色」：委派原来用紫色（`#8250df`），而宿主的语义色里
根本没有紫——它一眼就不像宿主的一部分。委派是「进行中」，归到强调色的软底即可。

#### 这条规则当时漏了两处，后来补齐

写这条规则的时候，「danger 够 4.5:1」这句话我只验了**纯底**，就顺手把 danger 当成
了可以当文字色的例外——于是「高」徽章与「委派逾期」这两个**红软底胶囊**仍然写着红字。
软底会把对比度再往下压：`#ec1313` 对纯白是 4.49:1（本来就只在线上），叠一层 5% 红软底
后是 **4.45:1**，就不达标了。

补齐之后，红的行内胶囊一律「**中性文字 + 红描边 + 红软底**」：红只承担形状与底色，
文字走 `--wb-fg`（实测 18.9:1）。这样做同时降低了噪声——原来列表里三行红字，现在
是三个红边小胶囊，视觉上安静得多，而红色信号一点没丢。

保留的唯一红字是**逾期日期**：它坐在纯底上（4.49:1），且是每行里唯一需要立刻行动的
信号，换成中性色会被埋掉。整幅告警条 `.dsh-wb-err` 也仍是红字——那是约定俗成的
告警样式，且信息不靠颜色单独承载。

教训是：**验对比度要验「最终的合成背景」，不是元素名义上的那个色**。`test/build.test.mjs`
新增了一条断言钉住这个（注意断言里不能直接查 `color:var(--wb-danger)`——
`border-color:var(--wb-danger)` 含同一子串，会把正确的描边误判成文字色）。

### 纵向密度：面板住在一个又宽又矮的地方

真实 `dsh web` 里量了容器尺寸后才意识到，这个面板的几何形状和我做演示时假设的完全不同：
底部工作台约 **1000px 宽**（窗口 1280 时），高度却很有限。也就是说**横向很富余、
纵向很稀缺**——密度不是审美偏好，是这个容器形状决定的硬约束。

这轮改样式的第一版恰恰在这里栽了：字符串比较「看着更透气」就把待办行从 24px 松到
27.5px，一屏少一条半任务。这种退化不报错、不失败测试、review 也看不出来，只有量数
才看得见。改回 24px（纵向内边距 4px→2px、行间距 2px→0）后：

| 指标 | 改动前 | 第一版（错） | 现在 |
|---|---|---|---|
| 待办行高 | 24.8px | 27.5px | **24px** |
| 筛选行高 | 37px | 49px（折成两行） | **33px** |
| 内容总高 @1004px | 601px | — | **581px** |
| 内容总高 @420px | 619px | — | **601px** |

顺手也修掉一个我自己引入的回归：芯片横向内边距从 8px 改到 12px 后，6 个筛选芯片
总宽 383px + 5 个间隙超过了行宽，**在 420px 窄宽下折成两行**（第二行只挂一个芯片）。
芯片横向内边距定为 6px、纵向补回 2px 后总宽 359px，窄宽下也稳在一行。

两个由此沉淀下来的做法：**改纵向间距前后都量 `.dsh-wb-body` 的 `scrollHeight`**；
**验窄宽健壮性要手动把演示块压到 420px**——因为默认宽度是 1000px，窄宽问题在默认
尺寸下根本不暴露。

### 一致性的收益：真机量出来的数

在真实 `dsh web` 里逐个量面板内**所有**文字元素与其**合成背景**的对比度
（WCAG 相对亮度公式）：**76 个文字元素，浅色最低 4.50、深色最低 5.55，两套主题都是
0 个低于 4.5:1**。最低的那两个就是逾期日期——有意保留的唯一红字。「高」徽章改用中性
文字后是 18.9:1。同时确认 `--wb-fg-2` 在 wrap 上确实随之翻转（`#61666b` → `#cfd3d6`）、
胶囊的 `corner-shape` 是 `round` 而非被 superellipse 压变形。

**量法本身有个坑，值得单独记**：最初的脚本是「沿祖先链找到第一个 alpha ≥ 0.999 的
背景就停」，这会**跳过 5% 这类半透明软底**，把对比度算高——「高」徽章的 4.45:1 就是
这样被算成 4.50:1「恰好达标」的，于是漏掉了那个真不达标的元素。正确做法是把祖先链上
的背景**按 alpha 逐层合成**再算。另一个坑：切换主题后要等 `--ds-transition-duration`
（.2s）走完再读 computed style，否则读到的是动画起点（见 AGENTS.md 坑 #20）。

## 测试分层：为什么 host 集成测试不可省

五层测试，各自挡不同的事：

| 文件 | 挡什么 |
|---|---|
| `store.test.mjs` | 数据层纯逻辑：递归遍历、迁移、进度、留档 |
| `host.test.mjs` | **真的把插件跑一遍**：真工具定义 + 真 HTTP 路由 |
| `logic.test.mjs` | 客户端纯函数，以及与 host 侧的跨半身一致性 |
| `client.test.mjs` | **假 React + 真构建产物里的面板组件**：渲染与手势接线 |
| `build.test.mjs` | 产物断言：导出形态、inject 声明、工具清单 |

`client.test.mjs` 是最后补的一层，补它的理由和前一层一样：面板曾经是唯一
只能靠人肉点的地方，而它恰好最容易出「一打开就白屏」——变量名打错、props 写错、
事件接错函数，`node --check` 只查语法，一个都挡不住。

做法是**不装 React**：写一个只实现用到的那些 API 的最小 React（`createElement`
加五个 hook），通过 bundle 工厂的 `require('react')` 注入，DOM 与 localStorage
也换成替身。于是被测对象是**构建产物里的真实组件**，不是它的复制品。

关键的一条纪律：**数据源不手写**。先用真 host 建计划、调 `plan_show` 拿真 payload
再喂给面板。手写的假 payload 少一个派生字段（比如 `type`），面板会静默走兜底分支，
测试就悄悄退化成什么都没测——**假数据的危险不在于假，而在于它比真的少东西，
而少的那部分恰好被兜底逻辑盖住了**。

这层测不了 CSS、真实浏览器的 DnD 行为与 React 的调度语义。它负责「接得对不对」，
不负责「长得对不对」——后者只能在 `dsh web` 里实测。


`host.test.mjs` 用一个假的 Cordis 上下文收集真实的 `tools.register` 与路由，
再按真实调用形态驱动它们。它存在的理由是一次实证：递归树改造中被它抓到两个
**纯函数测试与产物断言都抓不到**的 bug——

- `locate()` 对第三层节点返回了祖父而不是父节点。纯逻辑测试只测了「能定位到」，
  没测「parent 是谁」；而移动/删除都依赖这个 parent，错了会把节点挂到错误的位置。
- `moveNode()` / `removeNode()` 按标题调用时报「找不到节点 id」——工具层传标题、
  数据层只认 id，中间的解析被漏了。这个错**只在两层相接处**存在，
  任何单层测试都看不见。

结论与「静默失效」那条是同一个道理：**分层测试的价值不在于覆盖率，
而在于每一层能观察到上一层看不见的错误**。

第二批证据（落后预警与完成证据那一步）：写「进度跟上后落后标记应消失」的用例时
标记没消失，因为 `plan_node_set { current: 10 }` 把 `metric.target` 一并抹掉了。
**这个 bug 是「顺带」抓到的**——用例想验的是配速，而被测路径上一环合约出了问题。
纯数据层的 `metric` 测试全绿（它们都是整体写入，从来不会只写 `current`），
只有真跑工具、按真实参数形态调用时才会踩到。

第三层（`client.test.mjs`）到目前为止抓到的错**全在替身自己身上**：假的 Cordis
上下文把 `effect` 写成空函数（于是 tab 根本没注册），假 React 的 hook 槽位没在
挂载时重置（于是两块面板共用同一批 state）。**这条要如实记下来**——它说明这一层
当前的收益主要是「证明面板能渲染、手势接线对」，而不是「已经抓到过真实 UI 缺陷」。
真实缺陷要么已经在写测试的过程中被设计规避了（单击/双击的冲突就是这样想明白的），
要么还在等第一个。别高估它。

## 一次真实的教训：静默失效比报错危险

写 client 半身时照着 `logic.cjs` 的模式加了条件导出：

```js
if (typeof window === 'undefined' && module.exports) module.exports = { apply }
```

浏览器里 `window` 存在 → 条件为假 → `apply` 永不导出 → **面板不注册，
没有任何报错、没有任何日志**。这类 bug 靠人工 review 极难发现，因为代码
「看起来是对的」，而且运行时完全安静。

事后补了 `test/build.test.mjs` 直接对产物断言（必须无条件导出、
必须声明 inject、bundle 结构正确）。结论：**对「静默失效」类问题，
测试要断言产物，而不是断言行为**——行为测试在这种场景下根本跑不起来。
