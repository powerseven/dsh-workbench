# 设计说明

记的是**为什么这么做**，不是做了什么。用法见 [README](../README.md)，
架构与坑见 [AGENTS.md](../AGENTS.md)。

## 定位：为什么是插件而不是独立应用

需求是「基于 dsh web 界面做一个个人工作台」。有两条路：另起一个 web 应用，
或做成 dsh 插件。选了后者，理由：

1. **agent 天然在场。** 独立应用要自己接 LLM、自己管理会话、自己做权限。
   做成插件则直接复用宿主已有的会话、模型、工具审批、文件沙箱。
2. **AI 能主动读写计划。** 这是最大的收益：计划数据通过 `plan_*` 工具暴露后，
   agent 干完活可以自己回写进度。独立应用要做到这点，得额外设计一套 API
   让 agent 调用，而且 agent 还得知道它的存在。
3. **不需要另起服务。** 用户已经在跑 `dsh web`，插件只是组合树里多一行。

代价：绑死在 DSH 的插件机制上，且改动 host 半身需要重启。对这个场景值得。

## 数据模型：为什么 JSON 是真相、Markdown 是视图

计划是一棵需要**程序操作**的树：按 id 定位节点、删改、汇总进度、回滚版本。
两种朴素方案各有硬伤：

- **纯 Markdown 为真相**：人可读、可 diff、agent 能直接读懂。但要程序化增删改查
  就得写一个稳健的 Markdown 解析器；而任何格式漂移（用户手改缩进、agent 写错层级）
  都会**静默丢数据或改错节点**。风险与收益不成比例。
- **纯 JSON 为真相**：结构可靠、校验容易。但人不可读、git diff 不可读，
  agent 也得先解析才能理解——失去了「计划应该能被人一眼看懂」这个基本诉求。

双表示各取所长：**写入永远走结构化路径**（`plan.json`，有校验和版本归档），
**阅读与 diff 走生成的 `PLAN.md`**。代价是二者可能不同步 —— 但同步是单向的
（`PLAN.md` 每次写入都从 `plan.json` 重新生成），所以不会产生冲突，
只会在「有人手改了 PLAN.md」时丢失手改内容，这一点在文件头和 README 里都写明了。

## 结构：为什么是任意深度的树，而不是固定的三层

最早的模型是硬编码的三层 `goal → kr → task`。它的问题不是「不够灵活」这种笼统说法，
而是**三个具体后果**：

1. **层级是需求，不是约束。** 真实计划的分层深度取决于时间尺度——
   年度拆季度、季度拆月度、月度拆周，三层和四层都常见。写死三层等于
   让用户去迁就实现：把「季度」硬塞进 goal、「月度」塞进 kr，剩下的只能写进文本里。
2. **三套 API 做同一件事。** `plan_goal_add` / `plan_kr_add` / `plan_task_add`
   的差别只有「挂在谁下面」，字段几乎重合；agent 每建一个节点都得先判断
   「这算目标还是 KR」——而**这个区分对人本来就没有意义**，它只是实现的产物。
3. **结构约束散落在各处。** 「KR 不能挂 goal 之外的东西」「task 必须有父 KR」
   这类校验要在每个入口重复一遍，每加一种关系就要改所有入口。

改成**递归节点树**：节点只有两种类型 `plan`（容器，可挂子节点）与 `todo`（叶子），
`children` 递归下去，深度不限。收益是结构操作**收敛成四个**，全部作用在任意节点上：

| 操作 | 语义 |
|---|---|
| `node_add` | 建一个节点，`parent` 决定挂哪；不传就进收件箱 |
| `node_set` | 改字段（含 `type`——待办 ⇄ 计划） |
| `node_move` | 换父节点 / 调同层顺序 |
| `node_remove` | 删节点（计划连子项一起） |

「层级」从**结构**变成了**约定**：你想用三层就用三层，想用四层就用四层，
代码里没有一处知道或在乎这件事。代价是**每次遍历都得真的递归**——
早期实现里 `todoCounts` 只扫了顶层、`locate` 把祖父当成了父节点，
都是「按老的三层写」留下的 bug（见 AGENTS.md 坑 #9）。

**收件箱不再是独立字段。** 老模型里 `inbox[]` 和 `goals[]` 并列，是两个集合；
新模型里「顶层待办」就是收件箱——它是**一个位置**，不是一个类型。
这消掉了「收件箱项怎么归位」这类跨集合搬运算，归位退化成一次普通的 `node_move`。

## 换型：为什么允许原地改 type，且拒绝「有子的计划降级」

递归树里，`plan` 与 `todo` 的差别只有一条：**能不能有子节点**。
这条差别在真实使用中会随着认知变化——开会时随手记的「把数据治理做起来」，
事后发现得拆；拆完发现其实不该拆。所以换型是必须支持的，否则用户只能
新建一个计划再把待办搬进去，而多出来的那一层容器**没有语义**（它不是一件事，
只是「为了能拆而造出来的壳」）。

两条约束，理由不同：

- **有子节点的计划不能降级为待办**——待办是叶子，孩子们会变成孤儿。
  结构损伤不可逆，所以宁可报错。这个判断放在数据层（`setNodeType`）而不是 UI 里，
  UI 只是顺手把「⇩」按钮藏起来，避免让用户点了才看到错误。
- **跨类型状态必须重新归一**——`active` 只对计划合法，`todo`/`doing` 只对待办合法。
  这里踩的坑值得单独记：如果不归一，留下的是**一个对该类型非法的状态**，
  而非法状态在本项目里不是报错，是**渲染与统计里的静默错值**（进度算 0、
  筛选漏掉、角标对不上）。凡是「状态集合按类型分叉」的地方都要问一遍
  「跨类型时旧的取值还合法吗」。

## 迁移：为什么读时迁移，而不是写一个转换脚本

从 schema 1 换到 schema 2 会动到**用户已经写在磁盘上的 plan.json，以及
`.versions/` 里的历史快照**。做法上不是提供一个「升级命令」，而是
**读时自动迁移**（`migratePlan` 在 `PlanStore.load()` 里跑，落盘时写成新格式）：

- 要求用户跑一条命令，就会有用户没跑，而失败模式是**静默的**——
  旧的 `goals`/`krs`/`tasks` 字段读不出来，面板显示空计划。用户看到的
  是「我的计划没了」，而不是「请先升级」。
- 迁移必须**无损**：保持老的 id（`g1`/`k1`/`t1`）不变。因为委派、备注、
  快照文件名里都可能引用它们；重新编号会让历史快照指向错误的东西。
- `.versions/` 里的老快照**不迁移**，回滚时按同一套迁移逻辑读进来——
  少一次批量改写，也少一个「批量改写写坏了」的失败点。

## 进度：派生量，不落盘

`nodeProgress` / `planProgress` 都是**算出来的**，不存进 `plan.json`。

原因：一旦把进度存下来，它就会和任务状态不一致（改了任务忘了改进度），
而两个真相源之间的漂移是最难查的一类 bug。现在进度是树的纯函数，
不可能不一致。代价是每次读都要重算，但计划规模小，可忽略。

`nodeProgress` 对任意节点递归成立，这是递归树带来的简洁之处：

1. 有 `metric.target` → 按 `current / target` 量化；
2. 否则有子节点 → 取子节点平均（递归）；
3. 否则是叶子待办 → 按状态（`done` = 100%，其余 0%）。

两种度量（量化 / 清单）都保留，是为了同时容纳「可量化的 KPI」（完成 12 个台区）
和「清单式交付」（建立台账 = 若干步骤）。硬要统一成一种，
会逼用户给不可量化的东西编数字。

## 管控：为什么是警告而不是拦下

重要程度定为「高」时，产品上要求它必须有周期与负责人。实现上有两条路：
校验不过就**拒绝写入**，或者写进去但**把缺口指出来**。选了后者。

理由是这条产品目标：**「记下来」的成本要趋近于零**（见 PRD §2）。在捕获那一刻
硬拦，最有价值的行为——开会时顺手记一条——会变成一串表单校验，人干脆不记了。
计划烂尾从来不是因为缺一个必填校验，而是因为压根没记下来。

所以 `nodeWarnings()` 返回的是**建议**：agent 在工具返回值里看到它，
面板在节点旁显示 ⚠，仅此而已。缺口的补全由人和 agent 在后续交互中完成。

配套的两个细节也是同一思路：

- **默认 `normal`（中）**。若默认「高」，人人都是高，管控机制立刻失效——
  区分度比严格更重要。
- **待办不强制「负责人」**。待办默认就是自己负责；若硬要求填，每一条高优先级
  待办都会报警告，警告随即变成噪音。只有计划/子计划（需要有人对结果负责）才要求。

## 收件箱：为什么不计入计划完成度

`planProgress` 只对**顶层计划**求平均，顶层待办（也就是收件箱）不参与。两个原因：

1. **语义**：收件箱里的东西还没被承认为「计划」的一部分，把未归类事项计入
   完成度，等于让「没整理」这件事去拉低整体进度——惩罚的是记账习惯，不是执行。
2. **机制**：不计入完成度，但**计入角标、筛选与 `PLAN.md` 的收件箱段**。
   它会一直出现在你眼前，直到被归位或被完成。用「可见」而不是「扣分」来驱动整理。



## 版本留档：为什么不用 git 代替

用户选了「工作区 markdown/JSON + git」，git 本身就有历史。仍然自己做
`.versions/` 快照，理由：

- **不依赖 git。** 工作区可能没初始化 git，或这次改动根本没 commit。
  快照始终存在。
- **留档粒度是「每次变更」而不是「每次提交」。** agent 可能连续改十次才提交一次，
  中间态恰恰是最需要回滚的。
- **回滚代价低。** `plan_restore` 不需要懂 git。

两者互补：`.versions/` 管细粒度、可回滚；git 管跨文件、跨时间的项目级历史。

归档标签取**被归档版本自己写入时的原因**（`plan.lastReason`），而不是本次改动的原因。
这一点踩过坑：最初用本次改动的原因命名，导致标签描述的是「即将发生的事」、
内容却是上一个版本，回溯时会看错。

## 客户端：为什么纯逻辑单独成文件

`logic.cjs` 里放的全是无 React、无 DOM、无 IO 的纯函数（进度格式化、状态标签、
排序、汇总）。这样做是因为**这些逻辑最需要测试，而 React 组件在 Node 里测成本高**。
把它们抽出来后，可以用 `node:test` 直接覆盖边界情况（脏数据、未知状态、
空计划），且这些测试跑得极快（整个套件 < 1 秒）。

`logic.cjs` 被构建脚本内联进 bundle 闭包，UI 代码直接引用其中的函数名，
不经过模块导出——所以它可以用 `typeof window` 守卫来兼顾「Node 里测试」和
「bundle 里不导出」。**但 client 主文件不能这么做**，见 AGENTS.md 的坑 #1。

## 构建：为什么零依赖、不压缩

`scripts/build.mjs` 只做两件事：拷贝 host 的 ESM 文件，把 client 的纯逻辑与 UI
文本内联后包进 C6 工厂。不引入 tsdown/rollup/vite，不压缩不转译。

- 插件总代码量小，压缩收益近乎为零，而**可读的产物直接决定了排查效率**。
- 零构建依赖意味着 clone 下来 `node scripts/build.mjs` 就能跑，没有 `npm install`
  这一层失败点。
- 代价是没有类型检查。当前规模下，测试（170 个）比类型更能挡住真实缺陷 ——
  抓到的 bug（归档标签错位、client 导出被守卫吞掉、`locate` 认错父节点）
  都不是类型问题，而是「约定的含义在别处被理解错了」。

## 测试分层：为什么 host 集成测试不可省

四层测试，各自挡不同的事：

| 文件 | 挡什么 |
|---|---|
| `store.test.mjs` | 数据层纯逻辑：递归遍历、迁移、进度、留档 |
| `host.test.mjs` | **真的把插件跑一遍**：真工具定义 + 真 HTTP 路由 |
| `logic.test.mjs` | 客户端纯函数，以及与 host 侧的跨半身一致性 |
| `build.test.mjs` | 产物断言：导出形态、inject 声明、工具清单 |

`host.test.mjs` 用一个假的 Cordis 上下文收集真实的 `tools.register` 与路由，
再按真实调用形态驱动它们。它存在的理由是一次实证：递归树改造中被它抓到两个
**纯函数测试与产物断言都抓不到**的 bug——

- `locate()` 对第三层节点返回了祖父而不是父节点。纯逻辑测试只测了「能定位到」，
  没测「parent 是谁」；而移动/删除都依赖这个 parent，错了会把节点挂到错误的位置。
- `moveNode()` / `removeNode()` 按标题调用时报「找不到节点 id」——工具层传标题、
  数据层只认 id，中间的解析被漏了。这个错**只在两层相接处**存在，
  任何单层测试都看不见。

结论与「静默失效」那条是同一个道理：**分层测试的价值不在于覆盖率，
而在于每一层能观察到上一层看不见的错误**。

## 一次真实的教训：静默失效比报错危险

写 client 半身时照着 `logic.cjs` 的模式加了条件导出：

```js
if (typeof window === 'undefined' && module.exports) module.exports = { apply }
```

浏览器里 `window` 存在 → 条件为假 → `apply` 永不导出 → **面板不注册，
没有任何报错、没有任何日志**。这类 bug 靠人工 review 极难发现，因为代码
「看起来是对的」，而且运行时完全安静。

事后补了 `test/build.test.mjs` 直接对产物断言（必须无条件导出、
必须声明 inject、bundle 结构正确）。结论：**对「静默失效」类问题，
测试要断言产物，而不是断言行为**——行为测试在这种场景下根本跑不起来。
