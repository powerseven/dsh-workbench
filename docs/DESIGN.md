# 设计说明

记的是**为什么这么做**，不是做了什么。用法见 [README](../README.md)，
架构与坑见 [AGENTS.md](../AGENTS.md)。

## 定位：为什么是插件而不是独立应用

需求是「基于 dsh web 界面做一个个人工作台」。有两条路：另起一个 web 应用，
或做成 dsh 插件。选了后者，理由：

1. **agent 天然在场。** 独立应用要自己接 LLM、自己管理会话、自己做权限。
   做成插件则直接复用宿主已有的会话、模型、工具审批、文件沙箱。
2. **AI 能主动读写计划。** 这是最大的收益：计划数据通过 `plan_*` 工具暴露后，
   agent 干完活可以自己回写进度。独立应用要做到这点，得额外设计一套 API
   让 agent 调用，而且 agent 还得知道它的存在。
3. **不需要另起服务。** 用户已经在跑 `dsh web`，插件只是组合树里多一行。

代价：绑死在 DSH 的插件机制上，且改动 host 半身需要重启。对这个场景值得。

## 数据模型：为什么 JSON 是真相、Markdown 是视图

计划是一棵需要**程序操作**的树：按 id 定位节点、删改、汇总进度、回滚版本。
两种朴素方案各有硬伤：

- **纯 Markdown 为真相**：人可读、可 diff、agent 能直接读懂。但要程序化增删改查
  就得写一个稳健的 Markdown 解析器；而任何格式漂移（用户手改缩进、agent 写错层级）
  都会**静默丢数据或改错节点**。风险与收益不成比例。
- **纯 JSON 为真相**：结构可靠、校验容易。但人不可读、git diff 不可读，
  agent 也得先解析才能理解——失去了「计划应该能被人一眼看懂」这个基本诉求。

双表示各取所长：**写入永远走结构化路径**（`plan.json`，有校验和版本归档），
**阅读与 diff 走生成的 `PLAN.md`**。代价是二者可能不同步 —— 但同步是单向的
（`PLAN.md` 每次写入都从 `plan.json` 重新生成），所以不会产生冲突，
只会在「有人手改了 PLAN.md」时丢失手改内容，这一点在文件头和 README 里都写明了。

## 进度：派生量，不落盘

`krProgress` / `goalProgress` / `planProgress` 都是**算出来的**，不存进 `plan.json`。

原因：一旦把进度存下来，它就会和任务状态不一致（改了任务忘了改进度），
而两个真相源之间的漂移是最难查的一类 bug。现在进度是任务的纯函数，
不可能不一致。代价是每次读都要重算，但计划规模小，可忽略。

两种 KR 度量自动识别（有 `target` 走量化，否则走任务比例），
是为了同时容纳「可量化的 KPI」（完成 12 个台区）和「清单式交付」
（建立台账 = 若干步骤）。硬要统一成一种，会逼用户给不可量化的东西编数字。

## 版本留档：为什么不用 git 代替

用户选了「工作区 markdown/JSON + git」，git 本身就有历史。仍然自己做
`.versions/` 快照，理由：

- **不依赖 git。** 工作区可能没初始化 git，或这次改动根本没 commit。
  快照始终存在。
- **留档粒度是「每次变更」而不是「每次提交」。** agent 可能连续改十次才提交一次，
  中间态恰恰是最需要回滚的。
- **回滚代价低。** `plan_restore` 不需要懂 git。

两者互补：`.versions/` 管细粒度、可回滚；git 管跨文件、跨时间的项目级历史。

归档标签取**被归档版本自己写入时的原因**（`plan.lastReason`），而不是本次改动的原因。
这一点踩过坑：最初用本次改动的原因命名，导致标签描述的是「即将发生的事」、
内容却是上一个版本，回溯时会看错。

## 客户端：为什么纯逻辑单独成文件

`logic.cjs` 里放的全是无 React、无 DOM、无 IO 的纯函数（进度格式化、状态标签、
排序、汇总）。这样做是因为**这些逻辑最需要测试，而 React 组件在 Node 里测成本高**。
把它们抽出来后，可以用 `node:test` 直接覆盖边界情况（脏数据、未知状态、
空计划），且这些测试跑得极快（整个套件 < 1 秒）。

`logic.cjs` 被构建脚本内联进 bundle 闭包，UI 代码直接引用其中的函数名，
不经过模块导出——所以它可以用 `typeof window` 守卫来兼顾「Node 里测试」和
「bundle 里不导出」。**但 client 主文件不能这么做**，见 AGENTS.md 的坑 #1。

## 构建：为什么零依赖、不压缩

`scripts/build.mjs` 只做两件事：拷贝 host 的 ESM 文件，把 client 的纯逻辑与 UI
文本内联后包进 C6 工厂。不引入 tsdown/rollup/vite，不压缩不转译。

- 插件总代码量小，压缩收益近乎为零，而**可读的产物直接决定了排查效率**。
- 零构建依赖意味着 clone 下来 `node scripts/build.mjs` 就能跑，没有 `npm install`
  这一层失败点。
- 代价是没有类型检查。当前规模下，测试（54 个）比类型更能挡住真实缺陷 ——
  这次抓到的两个 bug（归档标签错位、client 导出被守卫吞掉）都不是类型问题。

## 一次真实的教训：静默失效比报错危险

写 client 半身时照着 `logic.cjs` 的模式加了条件导出：

```js
if (typeof window === 'undefined' && module.exports) module.exports = { apply }
```

浏览器里 `window` 存在 → 条件为假 → `apply` 永不导出 → **面板不注册，
没有任何报错、没有任何日志**。这类 bug 靠人工 review 极难发现，因为代码
「看起来是对的」，而且运行时完全安静。

事后补了 `test/build.test.mjs` 直接对产物断言（必须无条件导出、
必须声明 inject、bundle 结构正确）。结论：**对「静默失效」类问题，
测试要断言产物，而不是断言行为**——行为测试在这种场景下根本跑不起来。
